# 用 AI 做出顶级 UI 设计

这不是一个“生成一张好看的页面”的提示词，而是一套**先确认真正的问题，再扩大解法空间、建立设计身份、独立评审并完成工程验收**的生产流程（Harness）。你的任务不是让模型替你审美，而是把产品判断、审美判断和质量标准变成可观察、可比较、可迭代的决策；你同时是流程编排者：代码、图像生成、浏览器截图、独立评审、视频生成都是可调用的环节。Prompt 只解决一次任务，流程解决以后所有任务。

## 0. 先定交付边界

在开始生成前，先从用户上下文提取信息；缺失的信息用合理假设补齐，不要把一长串问题推回给用户。只有当两个方向会导致完全不同的成品时，才问一个最关键的问题。

写出一行 **Design Read**：

> 这是一个面向【受众】的【页面/产品界面类型】，解决【核心任务】，采用【视觉语言】，优先保证【业务/体验约束】。

同时建立 `brief`：

- **用户与任务**：谁在什么情境下使用，完成什么任务，成功是什么。
- **内容与状态**：真实文案/数据；loading、empty、error、success、disabled、权限不足、长文本。
- **平台与尺寸**：web / iOS / Android；桌面、平板、手机；触摸、键盘、读屏。
- **品牌与约束**：已有 logo、颜色、字体、素材、设计系统、不可改变的部分。
- **可信度与风险**：行业、敏感数据、付款/删除/发布等不可逆操作。
- **技术边界**：现有仓库、依赖、可用素材/API、不能泄露的密钥。

把“顶级”翻译成可检查的目标：任务清楚、层级明确、视觉有身份、交互可预测、状态完整、可访问、响应式不崩、实现能维护。不要把“高级感”当作唯一验收标准。

## 1. 设置三个设计旋钮

先根据 Design Read 设定并记录：

- `DESIGN_VARIANCE`：1–10，布局与视觉选择偏离常规的程度。
- `MOTION_INTENSITY`：1–10，动效的存在感。
- `VISUAL_DENSITY`：1–10，单位面积承载的信息量。

默认值为 `8 / 6 / 4`；严肃 B2B、公共服务、无障碍优先的产品降低 variance 和 motion，而不是为了“独特”牺牲可用性。

建立反默认护栏：不得无理由使用 AI 紫色渐变、居中英雄区、左文右图、三张等宽卡片、全屏玻璃、随机 glow、Inter + slate、空洞的“unlock/empower”文案。每次采用它们都必须说明它服务于什么任务。

同时建立**禁用词表**：Modern、Beautiful、Clean、Premium、高级、大气、简约、有质感——这些词几乎没有设计信息，禁止原样写进设计指令；每个词都要被翻译成具体的视觉决策（色彩角色、字体气质、间距节奏、材质来源）。

## 2. DISCOVER → DEFINE：先确认问题，再确定核心问题

不要把设计者想到的第一种解法误当成用户需求。完整的 Double Diamond 是四个阶段：

1. **Discover**：发散观察真实用户、场景和问题。
2. **Define**：收敛，定义一个值得解决的核心问题。
3. **Develop**：围绕核心问题发散多个解法、设计方向和原型。
4. **Deliver**：收敛、实现、验证并交付可用产品。

它不是一条从想法直达页面的直线，而是“发散 → 收敛 → 发散 → 收敛”。在 UI 工作中，第二个钻石才是设计方向和视觉表达的主要发生地。

### 2.1 建立问题 brief

先形成 `brief`，至少写清：用户是谁、使用情境、当前行为、真实痛点、成功信号、失败代价、不可逆风险、已有替代方案和非目标。用用户观察、访谈、真实反馈、已有数据或任务走查支撑，不要凭产品创作者的直觉直接宣布“用户需要这个功能”。

把问题写成可验证的任务陈述：

> 【哪类用户】在【什么情境】下，无法顺利完成【什么任务】，因为【可观察障碍】；如果解决，应该看到【成功信号】。

先列出多个问题假设，再聚焦一个核心问题。验证手段按成本递增：真实数据与日志、任务走查、少量代表性用户的可用性访谈、小规模灰度或 A/B 试用。AI 可以帮助整理证据和提出研究问题，但核心问题要有人确认；若核心问题尚未验证，不能用漂亮界面替代用户研究。

### 2.2 Develop：生成设计方向，不生成最终页面

围绕已经定义的核心问题，让模型先列出 8–12 个**互不相似**的设计语言，每个只写短描述：构图、材质、字体气质、颜色逻辑、动效隐喻、最适合的用户情绪以及它如何帮助完成任务。要求跨越产品、建筑、出版物、游戏、工业、自然、艺术装置等来源，避免只给“现代、极简、科技感”。

对每个方向做一次反向检查：

- 有没有可识别的核心隐喻，而不只是颜色和圆角？
- 能否支撑整个界面，而不只适合 hero？
- 是否会损害任务效率、可读性或信任？
- 是否至少在布局、信息密度、视觉媒介、交互隐喻中的两项与其他方向不同？
- 只换颜色/字体/图片的方向视为同一个方向，继续发散。

### 2.3 用外部随机性打破概率坍缩

当结果开始模板化时，可以生成一个**外部设计种子**，而不是只说“请随机、独特”。用 `scripts/create-design-seed.sh` 生成长字符串；让模型从字符串中寻找分组、重复、数字节奏等启发，只把它用于创意方向，不把字符串显示在产品中。种子增加的是搜索空间，不是质量。

视频讲解者也指出：随机字符串本身未必是关键，今天的模型只要收到明确的“多种不同色彩、布局、字体风格”要求，也能产生差异。真正重要的是让变化来自模型外部的明确输入，而不是期待模型自己突然变得随机。

推荐指令结构：

1. 生成外部随机种子，或明确指定多个互斥的变化维度。
2. 根据种子/约束提出颜色、构图、字体、材质、空间关系和动效的设计假设。
3. 保留 2–3 个最有潜力的假设，并说明取舍。
4. 让设计身份服务于产品任务，不要为了奇怪而奇怪。

并行变体：资源允许时（多会话/多终端可用），让同一 brief 用不同种子并行跑 3–4 个实例并排比较——单次输出里的“四个风格”仍受同一次预测的拘束，多个独立实例才能真正采样到设计空间的不同区域。单人单会话退化为文字方向发散即可，不为此阻塞流程。

### 2.4 把个人品味变成具体约束

不要只说“更高级”。说清楚：

- 我想让用户感到什么（从容、可靠、探索、掌控、温暖）。
- 借用什么外部隐喻（控制面板、像素游戏、等距城市、杂志、档案馆等）。
- 保留哪些特征；拒绝哪些俗套（例如“有触感但不要廉价拟物”，“有纹理但不要噪点背景”）。
- 哪些地方可以冒险，哪些地方必须熟悉（导航、表单、支付、删除）。

先选方向，再要求 AI 将方向压缩成一份 `design-identity.md`。如果设计身份已经足够清楚，可以直接在同一上下文中实现，不必机械地把 AI 生成的长提示词复制到新对话；换上下文的价值在于隔离角色和评审，而不是增加提示词搬运步骤。

两个好用的杠杆：

- 想打破常规布局时，直接给出“排版许可 + 任务底线”：允许元素贴边、溢出网格、不对称构图，但主任务路径必须仍然一眼可见。这比抽象的“更有创意”有效得多。
- 给约束时用具体设计指令，不用宏大形容词。“简化为图像为中心的网格、去掉发光效果和不必要的容器”比“追求 Apple 式极简风格”更有效；越依赖模型的执行力，越要把动作写成可执行的操作。
- **故意试“听起来不可能”的方向**：当你觉得“这肯定不行”时，往往正处在设计空间边缘；让模型试一次，它经常比你预计的做得好。不行就丢弃，代价只是一轮探索。
- **建立失败提示词库**：被淘汰的方向和提示词记录到 `prompt-graveyard.md`（内容 + 模型 + 失败原因 + 日期）。模型更新后重测它们——今天做不出的效果，下一代模型可能轻松做到；这是持续榨取模型能力的方式。

## 3. DEVELOP：选定身份，建立系统

从第二个钻石的多个解法和方向中选一条主线，不要把所有好点子拼成风格大杂烩。用下面的评分（0–5）比较候选：

| 维度 | 问题 |
|---|---|
| 任务清晰 | 用户是否一眼知道下一步？ |
| 身份强度 | 去掉 logo 后，是否仍有独特设计语言？ |
| 一致性潜力 | 能否扩展到列表、详情、表单和错误状态？ |
| 情绪匹配 | 是否与用户情境和品牌承诺相符？ |
| 可用/可访问 | 是否能在真实尺寸、输入方式和对比度下工作？ |
| 实现可行 | 是否能在当前技术与素材约束内稳定实现？ |

得分不是让模型替你决定；要求模型解释证据，人来做最终选择。

接着定义信息架构与关键路径：页面层级、主要任务、次要任务、内容优先级、组件状态、响应式变化。先画结构线框，再做视觉，不要让装饰掩盖信息架构问题。

若项目使用既有设计系统，使用它的官方组件和 token，不要只仿造外观。若没有，建立最小 token 集：颜色角色、字体、字号/行高、间距、圆角、边框、阴影、动效时长/easing、断点。每一个 token 都要有语义用途，不以屏幕上的随机颜色命名。

## 4. BUILD：分层实现，而不是一次生成

让实现者按这个顺序工作：

1. 真实内容与页面骨架。
2. 信息层级、布局、网格和响应式。
3. 组件与完整状态。
4. 设计身份（字体、颜色、材质、图像）。
5. 交互反馈和动效。
6. 多模态视觉资产。
7. 代码整理与可维护性。

### 4.1 内容先于装饰

用真实或接近真实的文案，主动测试长标题、空数据、超长列表、不同语言和错误信息。不要用 lorem ipsum 验收层级；文字长度就是布局约束。

AI 往往能生成结构，却很难写出真正属于产品的文案。核心标题、按钮、空状态、错误说明和品牌语气应由人审核，最好由人亲自写或至少重写；不要用抽象隐喻和“赋能、解锁、重新定义”填满界面。

### 4.2 组件必须有完整状态

至少覆盖：默认、hover、focus-visible、pressed、disabled、loading、empty、error、success、权限/网络异常。表单标签放在输入框上方，不把 placeholder 当 label；破坏性操作需确认、撤销或明确后果。

### 4.3 动效是解释，不是噪音

每个动效回答一个问题：它是否表达因果、状态、空间关系或注意力转移？交互反馈应快而克制；避免无限循环、同时出现多个视觉焦点、影响阅读的视差。实现 `prefers-reduced-motion` 降级，并检查首屏性能。

### 4.4 使用图片/视频/3D 资产时

代码生成的渐变、几何形状和重复纹理容易暴露模板感；当它们确实不能表达目标质感时，使用合适的图像或视频资产。资产要与身份、背景和裁切规则一致，不能为“丰富”而堆素材。API key 只放本地 gitignored 环境变量或受限密钥，绝不写进代码、截图、提交记录或交付物。

如果有视频模型，先定义首尾帧、循环方式、透明/抠像方案、移动端降级和文件大小；动态资产要逐帧检查，不能只看生成器预览。抠像技巧：让模型生成单色背景（如绿幕）的循环动画，再用 chroma key 或视频 matting 转成透明素材，即可像普通 UI 元素一样分层嵌入。滚动或指针驱动的逐帧播放（把视频进度映射到交互进度）可以做出一镜到底的页面体验；实现时必须定义帧序列、静态降级图、性能预算和移动端表现，且关键信息不能只存在于动画中。

## 5. 独立 CRITIC：隔离上下文，建立反馈闭环

实现者不能同时当自己的评审员。每一轮：

1. 截图当前页面（先过下方“截图管线检查”），在目标尺寸和关键断点各一张；必要时录制关键交互。
2. 新建干净上下文，只给截图、目标用户/任务、Design Read、设计身份和参考图；不要给代码、实现理由、旧评分或“请继续沿用”的心理负担。若平台无多模态读图能力，回退方案是让实现者把截图转成结构化视觉描述（有损，必须在评审记录中标注“文字代理评审”，其结论降级为参考）。
3. 让评审员先描述它认为的设计意图，再以统一 rubric 找最大差距，输出 3–7 条可执行改动；必要时要求给出伪代码、组件级改法或明确的结构调整，而不是只写审美形容词。
4. 实现者按优先级改动；一次只改变一组相关变量，保留前后截图。
5. 重跑评审并记录分数、改动、是否收敛。

### 截图管线检查（送评审前必须全部通过）

截图是 Critic 的唯一感官，管线失真会让评审“确认”不存在的 bug。硬检查四条：

1. **视口宽度=目标宽度**：不要信任无头浏览器的 window-size。macOS 上 Chrome headless 的 `--window-size=390` 实际按更宽的布局渲染（实测 756px，用注入脚本读 `clientWidth` 证实）。可靠方案：`npx playwright screenshot --channel=chrome --viewport-size=390,844 --full-page --wait-for-timeout=1500 <url> out.png`（复用系统 Chrome，零浏览器下载）。
2. **整页高度=scrollHeight**：用固定高窗口截图会产生画布余白，评审会把余白当成“布局空白”。用 `--full-page`；或注入脚本读 `document.documentElement.scrollHeight` 复核。
3. **像素宽=视口宽**：截图后用图像工具（sips/ffprobe）核对 PNG 宽度。
4. **动画已完成**：含入场动画的页面必须等动画完成（如 `--wait-for-timeout` 大于动画总时长）或以 reduced-motion 模式截图；半透明中间帧会被评审当成“残影渲染故障”和“对比度不足”。

评审员报告的事实性陈述（“文字被裁”“某元素缺失”“对比度不足”）需抽查复核后再执行修复——实测中评审员会误读颜色（把提亮红当成朱红报 2:1 对比度），也会沿用上一轮的印象。视觉异常先用 DOM 度量定位根因，再决定是改页面还是修管线。

复核图像细节时，**不要把整页长截图直接交给视觉模型提问**：实测中整页 3000px 长图上的小细节（便签是否旋转、小字是否可读）会被漏判，同一张图裁剪放大后结论反转。硬规则：复核局部细节一律先用图像工具裁出目标区域并放大 2–4 倍，再交给视觉模型；对颜色的判断不信目测，用像素取样或按 token 计算对比度。

评审员必须同时看大结构和细节，并主动惩罚：模板化布局、过度渐变/glow、无意义容器、装饰抢主任务、文案空泛、组件不一致、AI 生成的过度解释、缺状态、不可访问和响应式破坏。

评分采用维度分数，不允许用一句“很高级”替代证据。使用 `references/critic-prompt.md`。设定最多 3 轮自动迭代；连续两轮只在局部改动而总体分数不升时，回退到 Define 重新选方向。不要把“9/10”写给评审员诱导它报高分；停止条件由外层流程结合风险决定。

两条约束写进评审配置：

- **Critic 不为实现成本降低标准**：禁止评审员考虑“改起来麻烦”“工作量大”，它的唯一输入是画面是否达到目标质量。
- **控制评审预算**：评审模型只做判断，不做改写；健康状态下评审消耗应只占总输出 token 的一小部分（经验值 <10%）。若评审逐轮大幅增长，通常是实现者没有按优先级修改，或评审员越权改写设计。

选择评审模型看设计判断力，不看价格：用一轮小样本测试（同一截图交给两三个模型评审），选建议最具体、最能被实现者直接执行的模型。实践中，较强的通用大模型和某些设计见长的中型模型都可能是好的评审者，模型格局会变，角色协议不变。

参考图是质量基线和语法启发，不是复制目标。优先提供 3–5 张同类专业作品，并要求评审员比较 polish、层级、节制和任务适配。

## 6. DELIVER：Subtraction Pass → AI Tells Audit → 生产验收

完成独特方向后，按顺序做两轮专门的收敛审查，再进入验收清单。

### 6.1 Subtraction Pass（只删不加）

这一轮**禁止新增**任何元素、装饰、动画、颜色、标签或容器；只允许删除、合并、简化、弱化和重排。AI 非常擅长添加，却很少主动删除；“再优化一下”会被它理解成“再加点东西”，所以减法必须作为独立一轮提出并明确禁止新增。

对每个元素问三个问题：

1. 它是否承担真实的信息功能？
2. 它是否强化视觉层级或品牌语言？
3. 删除它之后，页面是否真的会变差？

三个问题都没有明确的“是”，就删除或合并。特别检查：无意义 glow/渐变、多余卡片、装饰形状、重复标签、无意义图标、多余 CTA、过度动画、散落的强调色。

文字与图形的取舍：图形已能传达信息就删文字；图标含义不明显时，补文字或 hover 提示，而不是硬删。平台原生控件通常优于更差的自定义实现。

### 6.2 AI Tells Audit

单独做一轮“AI 味”审查，不修改功能，只找一眼像 AI 生成的模式：紫色/蓝色渐变滥用、无作用的 glow、纯装饰性 glassmorphism、等宽卡片阵列、所有元素同一圆角矩形、pill 滥用、“左标题右大图” hero、“eyebrow→标题→段落→卡片”的机械节奏、为动画而动画、到处散落的强调色。

逐项记录：这个 tell 是什么、为什么显得模板化、应该删除、重构还是替换。目标不是把设计做得奇怪，而是让它看起来 **Intentional**（每个决定都有理由），而不是 **Generated**（模型顺手生成的）。

### 6.3 生产级验收清单

**体验与内容**
- 主要任务、下一步和当前状态一眼可见。
- 导航、反馈、撤销、错误恢复符合用户心智模型。
- 无重复意图的 CTA；按钮文案桌面端不换行。
- 真实内容、空/错/加载/成功状态均经过检查。

**视觉系统**
- 设计身份在所有页面、状态和断点保持一致。
- 字体层级、行长、对齐、间距、圆角、边框、阴影有规则。
- 只有一个主色彩策略；对比度与层级不是靠颜色堆砌。
- 首屏不被过大标题、超长文案或装饰挤出视口。
- 没有无法解释的 AI 默认套路。

**可访问性与响应式**
- 键盘可完成所有任务，focus-visible 清晰且不被裁切。
- 文本/控件/非文本对比度按 WCAG 2.2 检查；信息不只用颜色表达。
- 触控目标足够大且有间距；表单有 label、错误说明和关联关系。
- 缩放、动态字体、窄屏、横屏、长文本不重叠、不溢出。
- `prefers-reduced-motion`、语义 HTML、可读的替代文本已处理。

**工程与资产**
- 只使用项目已安装或明确批准的依赖；不混用设计系统。
- 图片有合适尺寸、懒加载和 fallback；视频有 poster、静音/暂停和移动端降级。
- 没有密钥、临时文件、调试面板或假数据混入交付物。
- 运行 lint、类型检查、构建和可用的自动化检查。
- 在目标浏览器和至少一个真实触控设备或模拟器检查关键路径。

## 7. 每次交付的工件

除成品外，保留可复用决策记录：

- `brief.md`：用户、任务、约束、假设、成功标准。
- `directions.md`：发散出的方向、种子、淘汰理由。
- `design-identity.md`：选定的身份与 token 规则。
- `critic-log.md`：每轮截图、维度分数、前三个改动、是否收敛。
- `qa.md`：断点、状态、无障碍、性能和浏览器检查结果。

如果用户只要一次性页面，也至少在回复中给出 Design Read、关键取舍、已验证范围和剩余风险；不要把随机生成当成设计过程。

若项目跨会话继续，维护 `prompt-graveyard.md`：淘汰的提示词、所在模型、失败原因和日期；每次大模型更新后重测一遍，把复活的方向放回探索池。
