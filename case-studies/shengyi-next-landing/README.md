# 案例：生意说 Web 首页互动化（`REDESIGN` + `COMPONENT` + `QA`）

它是一次真实任务的完整留痕，**不是**受控实验；不能用来证明这套 Skill 对新手或跨项目稳定有效。

## 做了什么

**问题**：产品最关键的差异点是「只有你确认过的内容才会继续往下走」。旧版首页用一行文字声明它，用一张静态示意卡展示它——访客只能读，不能做。首屏静态示意卡还和第二段「原话 / AI 整理 / 用户确认」三格轨道用同一句原话讲同一件事。

**改法**：把示意卡换成一个台面。

1. 6 个行当纸签（理发 / 早餐 / 水电 / 汽修 / 花店 / 宠物）切换演示原话；
2. 每句原话下方有一条 44 段声波，形状由该句文本**确定性派生**（不是随机），同一句每次渲染形状一致；
3. 按「就按这个理解」→ 状态翻成「已确认」→ 才渲染 3 条内容选题，可以展开看到「演示内容」开头；
4. 按「等等，我再改改」撤销 → 产物从 DOM 消失；
5. 切换行当会重置回待确认。

关键决定：**未确认时产物节点根本不存在于 DOM**（不是隐藏）。「确认才解锁」由结构表达，而不是再由一行文案声明。

配套的视觉判断：人说的话用衬线（Songti SC），机器的整理用无衬线；台面满宽出血、原话纸条轻微倾斜并溢出内容列；橙色实心只留给页面唯一转化 CTA，确认按钮改为白底墨边 + 橙色声音点。

## 结果

| 项目 | 优化前 | 优化后 |
|---|---|---|
| 独立 Visual Critic（单模型静态截图，0–10） | **5.0** | **6.6** |
| 可操作对象 | 0 个（全页只有 4 个链接） | 6 纸签 + 确认 + 撤销 + 3 条可展开选题，全部键盘可达 |
| 「未确认不进入生成」 | 一行文字声明 | 产物未确认时不在 DOM；撤销后消失 |
| 行当覆盖 | 1 句演示原话 | 6 个行当各 1 句 + 各自 3 条选题 |
| Engineering QA | — | **pass，阻断项 0**（`npm test` 933/933、ESLint 0 告警、生产构建通过） |
| 首屏契约（390×844） | 时长与积分底部 ≈800 | 时长与积分底部 799（主标题 189 / 台面 669 / 主 CTA 739） |
| 代价 | `/` 路由 917 B / First Load 107 kB | `/` 路由 2.18 kB / First Load 108 kB（约 +1 kB） |

Critic 的结论原话：**「机制只能被读到、不能被看到」被部分解决，方向对**；「确认即解锁」的因果在视觉上闭合且可核对。

## 这次流程真正抓到了什么

不只是「评分从 5.0 到 6.6」，而是**四类只有分轨验证才会暴露的缺陷**：

1. **新增表面引入的可访问性回归（QA 抓到）**：台面色 `#F1E9DE` 上，品牌蓝灰 `#5C6F87` 只有 **4.28:1**，低于 WCAG 2.2 AA 的 4.5:1；主会话按 sRGB 复算又发现整理块底色上为 **4.36:1**。修复方式是新增 `--landing-trust-ink: #4C5D74` 专用于小字，边框与结构线仍用 `#5C6F87`。复核：390 / 1440 / 320 三种视口、待确认 / 已确认 / 展开三种状态下，**低于 4.5:1 的文本节点为 0**。
2. **视觉层级冲突（Critic 抓到）**：首屏出现两个同尺寸实心主按钮（确认 + 橙色 CTA），且把「人拍板」的关键动作画成了机器色。
3. **修出来的新回归（合同测试抓到）**：为了让定义表底色出血，在文件前半段插入了一个 `@media (min-width: 768px)` 块，导致「第一个 768 断点」的位置提前，二维码合同断言的切片再也取不到 `.desktopQr{display:none}`。测试从 933/933 变 932/933，修复后复跑全绿。
4. **Critic 的两条事实性陈述不成立（主会话抽查抓到）**：Critic 断言「原话纸条完全水平、未溢出内容列」与「人话不是衬线体」，实测 `getComputedStyle` 显示纸条 `transform = rotate(-0.35deg)`、原话 `font-family` 首个可用字体为 `Songti SC`（`document.fonts.check` 返回 true）。两条均判 **reject**，且**不因此加大倾斜或更换字体**——那会破坏既有的克制契约。同一位 Critic 还有一条「桌面演示面板是内缩圆角卡」也与 DOM 实测（台面 `left=0 / right=1440`，满宽出血）矛盾。

第 1、3 条说明：**流程自己也会引入缺陷**，所以「改完再复核」和「改完重跑合同」不是礼节，是必需步骤。第 4 条说明：**评审员的陈述必须抽查**，不能整段照抄进结论。

## 结果边界（不能说明什么）

- **不能说明转化更好**：没有流量、没有 A/B、没有真实用户测试。任务走查在 QA 中明确标为 `NOT TESTED`。
- **不能说明真机表现**：截图与自动化都在 system Chrome（DSF 1）；微信内置浏览器、DPR 2/3 未测。
- **不能说明读屏可用**：DOM 语义与 ARIA 有自动化证据，但没有 VoiceOver/NVDA 走查。
- **不是生产验收**：改动只在本地工作树内，未提交、未部署。
- **没有性能预算数据**：只记录了 DOM 规模（185 个元素，声波占 45）、生产 HTML 31,493 B、17 个请求且 0 个外部域名；未跑 Lighthouse 或 trace。
- `6.6/10` 是**单一模型对静态截图**的判断，不是客观质量证书，也不能跨项目比较。

## 已接受风险（如实记录）

1. **RSC flight payload 携带完整演示数据**：渲染 DOM 干净（`curl` 剥掉 `<script>` 后无任何选题文本），但内联 flight payload 里有全部 6 个行当的选题与预览。这是「对外文案集中在 `page.js` 一处可审计、以 props 传给客户端岛」这条工程规则的必然结果；演示数据本身是公开的合成数据，不是用户数据。接受并记录。
2. **确认后页面变长、主 CTA 下移**：这是「确认才解锁」的因果本身，不是缺陷。
3. **320×700 首屏放不下全部内容**（时长与积分底部 882）：合同只覆盖 390×844。
4. **装饰性边框低于 3:1**（`待确认`/`开头` 标签芯片边、原话与整理块边框、分隔线）：其承载的信息由 ≥4.5:1 的文字表达。
