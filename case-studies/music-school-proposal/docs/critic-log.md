## 第一轮评审

`subagent:42ade7e4`，runtime 632.0s，**因 20 轮上限结束**（输出完整结论，非失败）。
结论：**needs-changes**。

### 主张 ①：移动端全页截图疑似重复了首屏内容

> 原话：「移动端所有整页截图疑似重复了首屏内容（320/390/768 三个断点都在同一设备像素偏移 16400 处与页面顶部高度自相似）」

**抽查结果：成立，而且是一个严重的管线缺陷。**

- 复现：`page.screenshot({fullPage:true})` 在本页 390×844@2x 下产出 780×25190 的图。按 DOM 实测位置裁剪（对照账簿在 CSS y=9438）得到的内容，与"真实滚动到该位置"的截屏**完全不同**。
- 定位：把 `scrollHeight × DSF` 降下来（DSF 1 → 12595px，低于 Chrome 约 16384 的纹理上限），同一位置的裁剪就正确了。
- 结论：**`fullPage` 在 device pixels 超过约 16384 时静默产出与页面不对应的图。** 图看起来正常，内容是错的。
- 验证方法（关键）：不要孤立地看一张可疑的裁剪图——把「全页图在某偏移的裁剪」和「真实滚动到该偏移的视口截屏」**并排放进同一张图**再问模型"这两张是不是同一内容"。视觉模型做**相对**比较远比做**绝对**判读可靠。（我在排查过程中被孤立裁剪图误导过两次：模型对着错误的图逐字转录出了页面早段的内容，而我一度以为它在幻觉。）
- 处置：新增 `scripts/fullpage.mjs`，改为**滚动分段 + 拼接**；`capture.mjs` 全量重拍；并用并排比对在三个位置（正文列表 / 对照账簿 / 落款）逐一验证对齐一致。
- **回修进 SKILL.md**：§6.1 新增「硬检查：全页截图不能用 `fullPage`，除非页面很短」；§6.3 新增「当评审员报告"截图本身有问题"时，先验证截图，不要先反驳也不要先采信」。

### 主张 ②：页面自身有一处肉眼可见的内容自相矛盾

> 原话：「正文『它有三个身份』vs 组件……」

**抽查结果：成立。**

- 源文档第二节正文写「它有三个身份，各得其所：」，紧接着的表格却列了**四个**：一位新家长 / 一位在读家长 / 一位老师 / 您。
- 这是**源文档自身的矛盾**，不是页面引入的。因为本任务的硬约束是"文案主体不得缺失或修改"，页面**原样呈现**了这个矛盾。
- 处置：不修改文案；在案例 README 与交付说明里显式上报，并说明"改一行源文档即可重新生成"。这是本案例里唯一一个**必须由作者定夺**的问题。

### 主张 ③（被驳回）：标题是"通用系统无衬线"

> 原话：「它读起来像通用无衬线……笔画末端是均匀的方头」

**抽查结果：不成立。**

- `getComputedStyle(h1).fontFamily` = `"Songti SC", "Noto Serif SC", STSong, serif`；
- 用 canvas 逐像素比对：`"Songti SC"` 与 `sans-serif` 在同一段文字上的墨量分别是 **5964 / 7017**，像素哈希不同——确实是两个不同的字面；
- 再把宋体、楷体、黑体、思源宋体、行楷五种字体**并排渲染并标注**交给同一个模型，它能正确区分并逐一分类。

所以这是"孤立缩略图判读不可靠"，不是字体没生效。**没有因为这条意见去换字体族。**

**但它带出了一个真问题**：宋体没有 600 字重，浏览器合成加粗会把笔画撑开、字腔糊住。处置是**改字号/字距与展示声部，而不是换字体族**：展示字体一律 400，标题与引用改用**楷体**（笔画本身带表情），并把「人声＝楷体 / 骨架＝宋体 / 正文＝PingFang」确立为三段式字体分工。改完再放大复核，标题被正确读成楷体。

### 主张 ⑤（采纳）：手机把时间轴四段藏进横向滚动

评审员指出 390 宽度下一次只看得到一张卡，第二张只露出约 50px，"可以滑"的提示几乎为零。**成立**，且更严重的是：四个节点里有两条是**提案正文原文**——把正文藏进需要横滑的容器，等于让读者可能永远读不到。
处置：<768 改为纵向堆叠（四段全部可见，用左侧编号列建立"时间轴"感）；≥768 才用横向滚动。

### 截图协议新增一条（已回修进 `SKILL.md`）

**`fullPage` 对 `position:fixed` 元素只渲染一次（页面顶部）。** 所以只要页面有固定顶栏/侧轨，即使 `scrollHeight × DSF` 远低于 16000，也必须用滚动分段拼接 —— 否则你会得到一张“固定元素凭空消失”的图，并据此得出错误结论（本轮评审就因此怀疑桌面侧轨不存在）。

### 一个必须写下来的证据边界

**对滚动驱动的页面做分段拼接全页图，本身就不是忠实表示。** 每个分段冻结的是不同的天光角度，拼起来的光带位置并不等于任何一次真实浏览。本轮评审正是把拼接图当成了单一状态，才得出“光不会动”的结论。结论：滚动驱动的视觉变化不能用全页图取证，必须用多个滚动位置的视口截图。

### 第四项：音色改成钢琴

用户追加要求：「应该用钢琴的声音作为页面互动的元素。」页面是音乐学校的提案，原来的双振荡器合成（正弦 + 三角 + 低通）确实像电子铃而不是钢琴。

因为页面硬约束是**单文件、零外部请求**，不能用采样，改用**加法合成**现场造钢琴：非谐泛音（f_n = n·f0·√(1+B·n²)，B≈0.0006）+ 高次泛音先衰减 + 6ms 高通噪声当槌子击弦 + 同音双弦微失谐（±0.16%）制造拍音 + 按频率取延音长度；总线上加了 `DynamicsCompressor`（一个音 12 个振荡器，16 音旋律会重叠）。

**音色不能只靠“我听着像”验收**，所以写了 `scripts/verify-piano.mjs`：从页面抽出**真正在跑的那段合成代码**，离线渲染后做频谱与包络测量。实测非谐偏差 +1.8 / +6.4 / +13.3 / +28.0 / +33.5 cents（随次数递增）、起音峰值 7ms、开头 5ms 有宽带瞬态、旧版在 3/4/5/8 倍处的能量只有新版的 1/210–1/399。**全部 PASS。**

但要说清楚：这证明的是**频谱与包络符合钢琴模型，不等于好听**。
